# Skill-manager extraction practice

## Requested outcome

The user required five local Skill-enablement commits to leave the active DeepSeek Harness branch while preserving their desired behavior as an independently owned meta-intent plugin. Any necessary Host intrusion had to become the plugin's smallest compatibility patch with nearby source locators. The static package-specific Remote mount had to disappear in favor of a general contribution seam. The plugin then had to be installed and shared catalogs regenerated without losing existing right-sidebar, preset-manager, or other uncommitted interventions.

## Investigated reality

- Official Harness commit `b150a551b8d465e31e418e1b2eaf5e79bbb7d28e` was exactly five commits behind the local Skill-enablement assembly.
- Product behavior could move into one external Host/Web package. The remaining Host compatibility needs were runtime Skill invocation overrides and all-layer listing, one logged session choice consumed by the first-step catalog gate, and one lifecycle-owned conversation slot.
- The Host already exposed `TypertClientRemote.$mount(contribution)`. This was the needed generic Remote contribution seam; adding a second registry or retaining a static import would have duplicated authority.
- Existing local plugins independently owned other dirty Harness regions and shared generated catalogs. The catalogs therefore had to be regenerated from the composed source rather than assigned to the new patch.

## Realization and cutover

`/root/dsh-skill-manager` now owns the Skill-manager Host logic, generated Remote, command/settings writes, Web settings and first-step surfaces, build/install lifecycle, and an exact compatibility patch. Every intrusive patch region is bounded by nearby `dsh-skill-manager` locator comments, while an exact Git-private receipt—not the comments—records install ownership.

The browser contribution mounts its own generated Remote using the existing generic mount capability. `@deepseek-ai/dsh-api-remotes` has no package-specific Skill-manager import or mount.

The active Harness branch was reset to the official commit, and the pre-existing uncommitted intervention set was restored with matching pre-cutover diff and status digests. Setup then composed the new seam, regenerated catalogs, rebuilt affected artifacts, and linked the package into the `web` profile. The service was not restarted and no test suites were run, so user-visible runtime acceptance remains open.

## Protocol consequence

This practice strengthens the evidence for nearby purpose-comment locators plus external ownership receipts. It also shows that a package should reuse an existing generic contribution capability when that capability already supplies lifecycle ownership; a new static or registry seam is not justified merely to make one extracted package visible. This is realization evidence, not authority to revise or adopt a new protocol.
