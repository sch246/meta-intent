# Intent, STATE and LOG evidence

Date: 2026-09-01

## Attributable user decisions

The user defined STATE as an actionable, detailed and condition-expanded prompt rather than a minimal feature list:

> STATE的本质就是描述精确，条件展开的一组Prompt，而LOG则是用于决策STATE的决策依据

The user distinguished a conditional desired state from the feedback action caused by changing conditions:

> 一个是状态（条件STATE），一个是动作（条件变化时反影响STATE）

The user gave the applicability example that if a desired decision exists only under a particular framework, STATE retains that conditional relation; a target without that framework or concept must not manufacture it merely to satisfy the old words.

The user defined meta-intent as a response to implementation debt under frequent incompatible change and extreme cross-platform or cross-language reimplementation. Intent is retained while code is disposable. For a destructive update, the stated sequence is to discard prior changes as implementation inputs, obtain the latest target, check current availability, align intent and iterate STATE, then apply a new realization.

The user clarified that STATE itself may accumulate because it is a living operating guide rather than a dead snapshot. The present accumulation problem is LOG content that never represented an actual event or authorized decision.

The user limited immutability to truthful evidence of what happened: attributable user decisions, reality conditions that actually held, and alternatives that were actually weighed or rejected. An Agent hypothesis or draft has no authority merely because it was written or committed. If retained for investigation value, it must be identified honestly as a hypothesis or proposal. A false attribution or unadopted Agent inference may be corrected or removed; doing so does not rewrite history because that content never truthfully recorded history.

## Scope of this record

This record preserves only the attributable user decisions above. It does not adopt additional Agent or quoted-model proposals about mandatory STATE contraction, reversing the existing feature-inventory policy, verification machinery or the primary purpose of LOCK.
