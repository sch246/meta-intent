# Protocol tension report: 0.1 evidence audit

Record ID: `SRC-2026-08-25-PROTOCOL-0.1-TENSIONS`

Status: Agent investigation report against meta-intent protocol 0.1. It records checked limits and candidate consequences; it is not a user decision, protocol revision, or adoption event.

## Scope and evidence boundary

The investigation covered the public repository at commit `29f22eaa9732e1093c02b940254fb887a2cf15c2`, the bundled validator and twelve tests, the right-sidebar reference package, the local `/root/dsh-right-sidebar` checkout, the `/root/deepseek-harness` target checkout, and the publication event. It used static inspection, content digests, Git state, validator execution, and `git apply --check`/`--reverse --check`.

It did not execute a real installation-maintenance-uninstall cycle, mutate the Harness target, establish legal conclusions about licensing, or semantically approve protocol 0.1.

## T-1: protocol-byte propagation is deep and should be batched

Changing one byte of `PROTOCOL.md`, while holding revision, state semantics, logs, tests, and all other artifacts fixed, has a mechanically verified lower-bound propagation cost of six files:

1. `PROTOCOL.md`;
2. root `state/STATE.json`;
3. sidebar-example `state/STATE.json`;
4. template `state/STATE.json`;
5. `inputs/state/STATE.json`;
6. `LOCK.json`.

Five digest fields inside `LOCK.json` change: the state-entry snapshot, protocol implementation, protocol artifact, sidebar-example state artifact, and template state artifact. The graph terminates because state binds the protocol artifact rather than the digest of `LOCK.json`.

This is the pure digest-propagation lower bound, not the total cost of a legitimate semantic protocol revision, which may also require revision changes, provenance, state changes, tests, and migration evidence. The operational consequence is to investigate and record related tensions before synthesizing one coherent protocol revision instead of repeatedly paying propagation cost for isolated prose edits.

## T-2: provenance growth is coupled to every current lock

For a current lock, `validateLogBindings` requires the lock's log set to equal `STATE.json.logs`, while `validateStateBinding` requires byte-equal current state snapshots. Adding one selected log therefore invalidates every current lock until its bindings are regenerated.

At the investigated revision there is only one current lock, the candidate protocol lock, so adding one log has a four-file mechanical cost: the log, `STATE.json`, its snapshot, and `LOCK.json`. Examples and templates do not select the meta package's logs.

The protocol prose requires locks to name selected source logs with digests but does not state the validator's exact-set rule as explicitly as the implementation enforces it. A later revision must decide whether exact provenance equality is a constitutive requirement or an implementation choice, and how historical realization validity relates to newly accumulated provenance. No relaxation is authorized by this report.

## T-3: the realization half has no positive instance

The repository contains zero persistent `kind: realization` lock bundles, zero active locks, and zero positive realization conformance tests. The sidebar example and template both have empty `locks` directories.

One negative synthetic test constructs an accepted historical realization, executes realization target/state/log/acceptance validation, and deliberately fails because its authority log is not among its governing logs. Thus the realization code path has some negative structural coverage, but installation, maintenance, composition, staleness, last-good behavior, and uninstall have no positive end-to-end evidence.

This leaves `META-007` and `META-008` unsupported by realization evidence. The candidate lock's `acceptance.status: incomplete` accurately reflects that boundary. Before protocol adoption, a real right-sidebar realization should exercise linked installation, a shared profile manifest, the tracked Harness source patch, target drift, maintenance, and safe uninstall in an isolated target.

## T-4: publication widened the consumer scope without resource realignment

The meta state declares `file:///root/deepseek-harness` and `file:///root/dsh-right-sidebar`. These URIs have always been host-local; publication did not change their original applicability. Publication changed the other side of the relation by adding remote consumers who cannot resolve them.

State prose already calls them non-portable bootstrap resources, so this observation alone does not falsify `META-001`. The machine-readable declarations nevertheless lack an applicability scope and portable evidence identity, and validator resource checks only require non-empty `id`, `kind`, and `uri`. The public repository therefore exposes a consumer/resource scope mismatch that structural validation cannot report.

The same publication event fixed repository name and visibility while state continued to list both as open. GitHub reports no detected license; the legal consequence of that fact is outside this investigation.

## T-5: applicability is a relation whose either endpoint may move

Protocol 0.1 defines evidence and authority within declared scopes but does not explicitly separate a carried claim, its applicability to current conditions, and its authority in the receiving scope.

Observed failures include importing a user decision from another conversation as though locally governing, assuming that no adopted protocol existed before inspecting the repository, and expanding a package's consumer population beyond its host-local resources. These failures are silent because neither a moved claim nor a moved reader necessarily produces a structural error.

A later protocol candidate should preserve provenance while requiring applicability and authority to be established for the current package, target, and state scope. The rule must cover both directions: information moving into a new scope and a new consumer or target moving toward information whose scope has not changed.

## T-6: closed validator enums exceed or underrepresent protocol prose

The protocol describes root presentation/community files with examples using “such as”; the validator implements a closed six-name allowlist. Conventional files outside that list, including `CHANGELOG.md`, `AUTHORS`, and `NOTICE`, are rejected even though the protocol prose does not declare those names forbidden.

The protocol ontology also describes several authority-event roles, while `validateAuthority` accepts only `decision: approved`. Candidate-lock authority content is not schema-checked until a lock becomes accepted, allowing arbitrary pending values to appear machine-shaped without validation.

A later revision should either make closed sets explicit protocol commitments or make the validator follow role-based/extensible declarations. Authority evidence must distinguish approval, permission, semantic revision, retirement, and pending review without letting a validator invent authority.

## T-7: classification has no unresolved investigation state

Section 4.1 and `META-005` enumerate six maintenance classifications. None represents an investigation whose evidence is incomplete or temporarily unavailable. `verified_no_change` cannot serve because it requires verification; choosing the nearest class would manufacture certainty.

Maintenance later contains `blocked`, but that lifecycle branch is not integrated with classification. A later candidate needs an explicit report/stop condition for unclosed classification, or a general rule that incomplete evidence remains provisional and cannot be forced into a semantic branch. This is an anti-fabrication boundary, not necessarily a seventh substantive cause.

## T-8: staleness is stored but neither fully computed nor validated

`stale` is a lock-status enum and cannot appear in `activeLocks` or `candidateLocks`. Such a lock is therefore non-current, and the validator compares non-current locks only with their own frozen inputs rather than current state. Conversely, an unreferenced historical lock may remain marked `accepted` even when current state has advanced.

Staleness contains a mechanically decidable part—state, protocol, snapshot, and artifact identity—and a reality-dependent part—target drift, permissions, composition, and whether evidence still supports the claim. Protocol prose describes applicability in derived terms, but schema compresses both halves into one unverified value.

A later revision should compute the decidable mismatch, preserve unresolved reality-dependent applicability, and avoid presenting an unchecked status string as proof. Historical acceptance and current applicability must remain distinct.

## Shared protocol-level consequence

These observations are signals for protocol investigation, not direct state-writing rules. Mechanically decidable predicates may establish bounded conclusions; proxy signals must not be promoted into semantic conclusions until competing explanations are classified. Candidate changes should be synthesized together, tested against positive realization evidence, and presented for user adoption as a separate revision.
